# Спецификация дата-продуктов и хранилищ (data-product-spec)

Спроектировать дата-продукт в парадигме Data Mesh: витрины данных, ETL/ELT пайплайны, контракты данных (Data Contracts), SLA качества и документация для аналитиков и ML-команд.

## Процесс

1. **Определи ценность и потребителей дата-продукта:** Выдели стейкхолдеров (BI-аналитики, ML-инженеры, продуктовые PM) и сценарии использования данных.
2. **Спроектируй контракт данных (Data Contract Schema):** Описание структуры таблиц, типов полей, первичных ключей, допустимых значений (Enums) и ограничений Not Null.
3. **Зафиксируй соглашение об уровне обслуживания данных (Data SLA):** Время обновления данных (Freshness / Latency), частота выгрузок, допустимая задержка синхронизации.
4. **Опиши автоматические проверки качества данных (Data Quality / Great Expectations):** Проверка на дубликаты, аномальные выбросы, целостность внешних ключей и пропуски.
5. **Спроектируй Data Lineage и каталог метаданных:** Отслеживание источников происхождения данных от сырых логов до финальной витрины.
6. **Сохрани артефакт** в текущей рабочей директории как `data-product-spec-[контекст].md`.

## Формат вывода

### 1. Спецификация контракта данных (Data Contract)

| Название поля витрины | Тип данных | Ограничение (Constraint) | Описание бизнес-сущности | Источник в сырых логах |
| :--- | :--- | :--- | :--- | :--- |
| [`user_id`] | [UUID / BIGINT] | [Primary Key, Not Null] | [Уникальный сквозной ID пользователя] | [`raw_events.user_id`] |
| [`order_gmv_rub`] | [DECIMAL(12,2)] | [Check: ≥ 0.00] | [Сумма заказа с учетом всех скидок] | [`billing.transactions.amount`] |
| [`event_timestamp`] | [TIMESTAMP UTC] | [Not Null, Past only] | [Точное время совершения транзакции] | [`kafka.orders.event_time`] |
| [`payment_status`] | [VARCHAR(32)] | [Enum: 'paid', 'refund'] | [Финальный статус оплаты заказа] | [`billing.payments.status`] |

### 2. Спецификация Data SLA и проверок качества (DQ Checks)

| Тест качества данных | Инструмент проверки | Порог срабатывания | Реакция системы при сбое |
| :--- | :--- | :--- | :--- |
| [Freshness (Свежесть)] | [Airflow SLA Miss Alert] | [Задержка данных > 60 мин] | [Алерт дежурному дата-инженеру] |
| [Uniqueness (Уникальность)] | [Great Expectations] | [Duplicate Keys > 0%] | [Блокировка обновления витрины в BI] |
| [Completeness (Полнота)] | [Null Value Ratio Check] | [Nulls в критических полях > 0.01%] | [Остановка пайплайна + откат] |

### 3. Метрики эффективности дата-продукта
- **Data Freshness / Latency:** Время от совершения события в проде до появления в витрине данных.
- **Data Quality Score (Pass Rate):** Процент успешно пройденных тестов качества данных в пайплайне.
- **Data Product Query Volume:** Количество уникальных запросов и пользователей витрины за неделю.
- **Incident Time to Detect (MTTD):** Время обнаружения ошибки в данных до того, как ее заметят бизнес-пользователи.

## Правила

- Запрещено вносить изменения в схему витрины данных без предварительного согласования с владельцами контракта.
- Каждая витрина данных обязана сопровождаться автоматическими тестами целостности (Great Expectations / dbt tests).
- Архитектура требует строгого разделения слоев сырых данных (Bronze), очищенных (Silver) и витрин (Gold).
- Не допускай хранения незамаскированных персональных данных (ПДн) в открытых аналитических слоях.
- Максимальное допустимое время восстановления витрины из бэкапа (RTO) не должно превышать 4 часов.
