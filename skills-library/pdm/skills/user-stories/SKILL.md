# Написание пользовательских историй и критериев приемки (user-stories)

Спроектировать безупречные пользовательские истории (User Stories) по стандарту INVEST и критерии приемки по методологии BDD / Gherkin (Given-When-Then): разделение ролей, краевые случаи (Edge Cases) и декомпозиция крупных историй.

## Процесс

1. **Сформулируй каноническую историю по формуле Коннера:** «Как [Роль / Персона], Я хочу [Действие / Функциональность], Чтобы [Бизнес-ценность / Профит]».
2. **Проверь историю на соответствие критериям INVEST:** Independent (Независимая), Negotiable (Обсуждаемая), Valuable (Ценная), Estimable (Оцениваемая), Small (Компактная на 1-3 дня dev), Testable (Тестируемая).
3. **Разработай критерии приемки по синтаксису Gherkin (BDD Scenarios):** Сценарии Given (Дано: начальное состояние) -> When (Когда: действие пользователя) -> Then (Тогда: ожидаемый результат системы).
4. **Детализируй негативные сценарии и краевые случаи (Negative & Edge Cases):** Поведение при обрыве сети, невалидных данных, превышении лимитов и таймаутах.
5. **Декомпозируй крупные истории (Story Splitting):** Разделение эпиков по шагам рабочего процесса, типам данных или бизнес-правилам.
6. **Сохрани артефакт** в текущей рабочей директории как `user-stories-[контекст].md`.

## Формат вывода

### 1. Формуляр пользовательской истории (INVEST User Story)

#### Пользовательская история:
**Как** [авторизованный покупатель интернет-магазина],  
**Я хочу** [сохранить несколько адресов доставки в моем профиле],  
**Чтобы** [быстро выбирать нужный адрес на чекауте и не вводить данные заново каждый раз].

---

### 2. Спецификация критериев приемки (Acceptance Criteria / Gherkin BDD)

#### Сценарий 1: Успешное добавление нового адреса (Happy Path)
- **Given (Дано):** Пользователь находится на экране «Мои адреса» в личном кабинете.
- **When (Когда):** Пользователь вводит валидный адрес через подсказки Dadata и нажимает кнопку «Сохранить».
- **Then (Тогда):** Новый адрес появляется в списке сохраненных, отображается тост «Адрес успешно добавлен», данные сохраняются в БД.

#### Сценарий 2: Попытка сохранения неполного адреса без номера квартиры (Edge Case)
- **Given (Дано):** Пользователь указал улицу и номер дома, но оставил поле «Квартира» пустым в многоквартирном доме.
- **When (Когда):** Пользователь нажимает кнопку «Сохранить».
- **Then (Тогда):** Система подсвечивает поле «Квартира» предупреждением: «Пожалуйста, укажите квартиру для точной доставки курьером».

#### Сценарий 3: Превышение лимита сохраненных адресов (Negative Case)
- **Given (Дано):** У пользователя уже сохранено 10 адресов (максимальный лимит системы).
- **When (Когда):** Пользователь пытается добавить 11-й адрес.
- **Then (Тогда):** Кнопка «Добавить адрес» неактивна, выводится подсказка: «Удалите неактуальный адрес для добавления нового».

---

### 3. Метрики эффективности написания пользовательских историй
- **Story Rejection Rate:** 0% историй, возвращенных разработчиками из-за неполноты или двусмысленности требований.
- **Acceptance Criteria Test Coverage:** 100% покрытие критериев приемки автоматизированными E2E тестами.
- **Average Story Cycle Time:** Время реализации одной истории разработчиком (не более 2-3 рабочих дней).
- **INVEST Compliance Score:** Соответствие разработанных историй всем 6 принципам качества INVEST.

## Правила

- Запрещено передавать историю в спринт без оформленных критериев приемки в формате Given-When-Then (Gherkin).
- Каждая пользовательская история обязана нести самостоятельную ценность для конечного пользователя (принцип Valuable). Технические задачи и архитектурный техдолг без прямой ценности для пользователя (например, «переписать бэкенд на микросервисы») запрещено маскировать под User Story — их следует оформлять как Technical Enabler / Architectural Spike либо переформулировать через измеримый пользовательский Outcome.
- Если пользователь дает размытый запрос без контекста: запрещено выдумывать историю вслепую, запроси проблему пользователя, целевую персону и сценарий использования.
- История строго требует наличия минимум 2 негативных сценариев обработки ошибок или краевых случаев (Edge Cases).
- Не допускай создания историй размером более половины емкости спринта (слишком крупные истории обязаны дробиться).
- Формулировка роли обязана указывать конкретную персону («Авторизованный покупатель») вместо абстрактного «Пользователь».
