# Стратегия управления фича-флагами и релизами (feature-flag-strategy)

Спроектировать процессы управления функциональными флагами (Feature Flags / Toggles): канареечные релизы (Canary Releases), A/B тестирование, темные запуски (Dark Launches), правила очистки техдолга и аварийные рубильники (Kill Switches).

## Процесс

1. **Классифицируй типы фича-флагов:** Раздели флаги на Release Toggles (краткосрочные для выкатки), Experiment Toggles (для A/B тестов), Ops/Kill Switches (долгосрочные рубильники) и Permission Toggles (по ролям).
2. **Спроектируй стратегию постепенного развертывания (Percentage Rollout):** Схема раскатки: 1% (Internal/Dev) -> 5% (Beta) -> 25% -> 50% -> 100% с авто-паузой при росте ошибок.
3. **Настрой аварийные рубильники (Automated Kill Switches):** Автоматическое мгновенное отключение фичи при всплеске 5xx ошибок или деградации Latency.
4. **Опиши таргетинг и правила сегментации флагов:** Включение по User ID, версии приложения, региону, бета-группе или атрибутам компании в B2B.
5. **Сформируй регламент очистки устаревших флагов (Flag Cleanup SLA):** Удаление временных Release-флагов из кодовой базы в течение 14 дней после 100% раскатки.
6. **Сохрани артефакт** в текущей рабочей директории как `feature-flag-strategy-[контекст].md`.

### 2. Спецификация канареечной раскатки (Canary Release Pipeline)

| Шаг раскатки | Доля пользователей | Время выдержки | Критерий перехода к следующему шагу |
| :--- | :--- | :--- | :--- |
| [Шаг 1: Canary] | [1% пользователей] | [2 часа] | [Error Rate ≤ 0.05%, Crash-free ≥ 99.9%] |
| [Шаг 2: Early Adopters] | [10% пользователей] | [6 часов] | [Latency p95 без изменений, 0 P1 багов] |
| [Шаг 3: Half Base] | [50% пользователей] | [24 часа] | [Бизнес-метрики и конверсии стабильны] |
| [Шаг 4: Full Release] | [100% пользователей] | [Постоянно] | [Успешное завершение релиза] |

### 3. Метрики эффективности Feature Flag инфраструктуры
- **Rollback / Kill Switch Latency:** Время от обнаружения инцидента до полного отключения флага в проде.
- **Stale Flag Debt:** Количество фича-флагов, находящихся на 100% раскатке более 30 дней без удаления из кода.
- **Change Failure Rate:** Доля релизов, потребовавших отката или экстренного отключения фичи.
- **Flag Evaluation Performance:** Время проверки состояния флага на клиенте/бэкенде.

## Правила

- Запрещено оставлять временные Release-флаги в кодовой базе более чем на 30 дней после достижения 100% раскатки.
- Каждый новый фича-флаг обязательно должен иметь явно указанного ответственного владельца (Owner) и дату экспирации.
- Система требует автоматического срабатывания Kill Switch при росте доли серверных ошибок более чем на 1% от нормы.
- Не допускай создания взаимозависимых вложенных фича-флагов во избежание комбинаторного взрыва состояний системы.
- Максимальное время распространения изменения состояния флага на все узлы кластера не должно превышать 10 секунд.
