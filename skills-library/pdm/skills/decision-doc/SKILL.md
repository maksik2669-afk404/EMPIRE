# Документирование архитектурных и продуктовых решений (decision-doc)

Спроектировать структурированный документ принятия решений (Architecture / Product Decision Record / ADR / RFC / DACI): контекст проблемы, рассмотренные альтернативы, матрица компромиссов (Trade-offs), итоговый выбор и план внедрения.

## Процесс

1. **Опиши контекст и формулировку проблемы (Context & Problem Statement):** Какая проблема возникла, почему ее нужно решить именно сейчас и каковы критерии успеха.
2. **Определи роли участников по модели DACI:** Driver (Ведущий), Approver (Утверждающий), Contributors (Консультанты), Informed (Информируемые).
3. **Сформируй перечень жизнеспособных вариантов (Options Considered):** Минимум 3 альтернативных решения (включая статус-кво: «Не делать ничего»).
4. **Составь сравнительную матрицу компромиссов (Trade-off Matrix):** Оценка каждого варианта по стоимости, скорости, масштабируемости, рискам и техническому долгу.
5. **Зафиксируй итоговое решение и план действий (Decision & Rollout):** Однозначный вердикт с подробным планом миграции и критериями отката (Rollback).
6. **Сохрани артефакт** в текущей рабочей директории как `decision-doc-[контекст].md`.

## Формат вывода

### 1. Формуляр продуктового решения (DACI Decision Record)

| Блок документа | Содержание и детали решения |
| :--- | :--- |
| **Название решения** | **[DDR-104: Выбор биллингового провайдера для глобальной экспансии]** |
| **Статус решения** | **[Утверждено (Approved) / Внедрение в Q3]** |
| **Команда (DACI)** | [Driver: PM Биллинга; Approver: CTO; Contributors: Head of Legal, FinDir; Informed: Вся команда] |
| **Контекст проблемы** | [Текущий эквайринг не поддерживает международные карты и подписки в евро/долларах] |

### 2. Сравнительная матрица рассмотренных альтернатив

| Критерий сравнения | Вариант 1: Stripe Billing | Вариант 2: Paddle (MoR) | Вариант 3: Собственный биллинг |
| :--- | :--- | :--- | :--- |
| [Скорость интеграции] | [3-4 недели (Готовые SDK)] | [2 недели (Берут налоги на себя)] | [6-9 месяцев (Своя разработка)] |
| [Комиссия провайдера] | [2.9% + $0.30 за транзакцию] | [5.0% + $0.50 (Включая налоги)] | [1.5% эквайринг + ФОТ команды] |
| [Налоговый комплаенс (VAT)] | [Требует интеграции с Avalara] | [Полностью закрыт провайдером] | [Ручная сдача отчетности в ЕС] |
| [Юридические риски] | [Низкие (Нужно юрлицо в ЕС)] | [Минимальные (Merchant of Record)] | [Высокие (Штрафы за валютный контроль)] |
| **ИТОГОВЫЙ ВЕРДИКТ** | **[ВЫБРАННЫЙ ВАРИАНТ]** | [Запасной вариант при срыве сроков] | [ОТКЛОНЕНО (Слишком дорогой CAPEX)] |

### 3. Метрики эффективности документирования решений
- **Decision Velocity (Days to Approve):** Время от создания черновика RFC до финального утверждения Approver.
- **Decision Reversal Rate:** Процент решений, пересмотренных или отмененных в течение 6 месяцев (Target: < 5%).
- **Stakeholder Alignment Score:** Оценка прозрачности принятия решений в команде.
- **Rollout Schedule Adherence:** Точность соблюдения дедлайнов внедрения утвержденного решения.

## Правила

- Запрещено принимать критические архитектурные решения без наличия строго одного утверждающего лица (Approver).
- Документ решения обязан содержать детальный анализ статуса-кво («Что произойдет, если мы ничего не изменим»).
- Каждое решение требует обязательного описания процедуры и условий отката (Rollback / Fallback Plan).
- Не допускай принятия решений в устных беседах без публикации согласованного артефакта в репозиторий знаний.
- Максимальный срок рассмотрения и сбора комментариев по RFC не должен превышать 5 рабочих дней.
